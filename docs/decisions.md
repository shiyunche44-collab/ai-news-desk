# 设计取舍和踩坑记录

面试讲项目时用得上的「3 个取舍」和「3 个坑」。坑都是搭第一版时真实碰到的；等你接上真实模型跑几天，再把自己遇到的补进来，那才是最有说服力的素材。

## 取舍

### 1. 哪里用 workflow，哪里用 agent

只有选题研究员是 agent，其余全是固定流程。

- 采集、去重：抓什么、怎么判重都是确定的，交给模型只会更慢、更贵、更不稳定。
- 写 → 核查 → 改写：顺序固定，不需要模型决定「下一步该核查了」。写成代码，出问题能精确定位到哪一步。
- 选题需要判断：哪条重要、要不要再读一篇原文、要不要换个关键词再搜。这才值得交给 agent 循环。

### 2. 单 agent 还是多 agent

用主从结构：主控是代码（`orchestrator.py`），四个子 agent 各管一段，上下文互相隔离。

- 好处：写手只拿到一条新闻的原文，不会被研究员读过的十几篇网页干扰，token 也省。每个子 agent 的提示词短、职责单一，评测也能分开做。
- 代价：子 agent 之间只能通过结构化数据交接（`ResearchPick`、`Draft`），信息有损失。所以交接的结构要设计好。
- 什么时候不该多 agent：任务短、步骤之间强依赖上下文的，拆开反而更差。

### 3. 自己写循环还是用框架

第一版不用框架，`agent/loop.py` 一百多行。

- 先手写，才知道框架替你做了什么：步数上限、重复调用拦截、错误回传、并行工具调用、收尾。面试被追问这些细节时答得出来。
- 第 7 周用 LangGraph 和 AgentScope 各重写一遍核查流程，再写一页对比：哪些地方框架更省事（状态持久化、断点恢复、可视化），哪些地方反而绕。

## 搭建时踩到的坑

### agent 读网页失败后反复重试，停不下来

真实数据试跑时，代理拦住了 GitHub 的一个接口，`fetch_url` 每次都报错，研究员就用同样的参数一轮一轮地重试。

靠循环的护栏停了下来：同样的参数调用超过 2 次就拦截并提醒模型换思路，连续两轮全被拦截就强制收尾（`stopped_reason = repeat_limit`）。后来又做了两处改进：抓 GitHub 仓库改读 README 原文，换一个地址重试；读失败的网址不再重读，换下一条候选。

### 注入检测误报

一个真实仓库的 README 里正常写着「system prompt」，被规则当成注入打了标。这说明规则检测只能当提醒，不能当拦截，否则会误伤正常内容。真正的防线是权限：agent 根本没有发布工具。

### 记账里存下的请求「自己变了」

agent 循环每一轮把同一个消息列表传给模型，之后又往里追加内容，结果记账和日志里存的「第一轮请求」也跟着变长了。改成每次传一份拷贝。这类 bug 不影响结果，但会让成本分析和排查全错。

### 去重丢掉的那条，第二天又冒出来

媒体转载的官方消息第一天被判为近似重复丢掉了，但没入库；第二天官方那条已经「采集过」被过滤，媒体那条就成了新的候选。改成丢掉的也入库并标成 dropped，近似重复也要和前几天采集的标题比。
