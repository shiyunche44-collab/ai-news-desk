# Wavefront：把 drafter 的 base 砍小，让 correction head 扛主力

  - 标题、作者、提交日期均与 arXiv 摘要页一致。
- ✓ 投机解码让廉价的 drafter 提出 token，再由目标模型并行验证
- ✓ DFlash、P-EAGLE 这类并行块 drafter 一次前向提出整个 block，但丢掉了 block 内 token 之间的依赖；DSpark 用顺序执行的轻量 correction head 恢复了一部分
- ✓ 作者实测 DSpark 发现该 correction head 在大多数位置会覆盖 base 的预测，经过目标模型完整 lm_head 的 base readout 基本只提供一个种子

  - 紧接上一句 Qwen3-8B 的语境，指代明确。
- ✓ 在 Qwen3.8-27B 上，Wavefront 比 DFlash2、DSpark、xPress 分别高 7.6%、10.6%、5.0%，在同样的长上下文提示上分别高 7.4%、5.8%、6.0%
  - 模型名「Qwen3.8-27B」与基线名「DFlash2」均按原文照录，原文如此。
- ✓ 当服务负载增长到并发 32 时，这些吞吐增益仍然保持

## 正文
arXiv 2611.31638（Huy Huu Nguyen、Xin Huang，11 月 23 日提交）提出 Wavefront：把投机解码 drafter 里经过 target 完整 lm_head 的 base readout 换成学出来的低秩 base，把算力挪到 correction head 上。

出发点是实测 DSpark——那个顺序执行的轻量修正头在大多数位置会覆盖 base 的预测，所以完整的 base readout 基本只提供一个种子。

Wavefront 让 correction head 在同一 block 内看到整个已草稿前缀，用几次并行的 Jacobi pass 求解；pass 数固定，draft 步骤就没有数据相关的控制流，在 vLLM 里连同 fused kernel 抓成单个 CUDA graph。

实测 Qwen3-8B，数学、代码、对话和 agentic 基准平均比 xPress、DSpark、DFlash 高 2.6%、10.7%、23.6%，SPEED-Bench 长上下文提示上高 9.6%、14.3%、28.9%；Qwen3.8-27B 上分别高 7.6%、10.6%、5.0%。并发到 32 增益仍在。

对普通开发者：值得借鉴的是「固定迭代次数去掉数据相关分支」这个工程手法，而非模型结构本身。

  - 该信息来自 arXiv 摘要页的 Comments 字段。

## 正文
arXiv 上有一篇论文提出 ContextLure：攻击者不用污染历史对话，只要旁观一段正常的良性对话、从中提取证据再构造注入，就能显著提高间接提示注入的成功率。

论文把难点拆成两步。第一步是选料，从 User/System Preferences 两个维度、用 3 种策略挑出有用的证据；第二步是把选中的信息包装成「为某个未授权动作找理由」，做法是一张 Urgency/Priority 矩阵，含 4 种改写策略。关键是攻击者并没有增加对先前轮次或注入本身的控制，只是重新组织了本来就在对话里的信息。

效果上，作者报告在 AgentDojo 上攻击成功率达到 67.4%，InjecAgent 上是 87.3%（论文自述的评测条件）。

值得关注的点在于它把防线往前推了一格：过去防注入主要盯着「内容有没有被投毒」，而这里被利用的对话历史是干净的。对普通开发者来说，只要 agent 会读历史对话又调用工具，就得假设历史里的任务结果、用户关切、操作约束都能被拿去当攻击弹药，只做输入侧过滤不够。
